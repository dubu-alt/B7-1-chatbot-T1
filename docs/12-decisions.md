## 1. access token 15분 · refresh token 1일

### 결정
- access token(JWT) `JWT_EXPIRE_MINUTES=15`
- refresh token `REFRESH_TOKEN_EXPIRE_DAYS=1`, 재발급할 때마다 새 토큰으로 교체(회전)되며 새 만료가 다시 1일

### 근거
1. **access token 은 서버가 폐기할 수 없다.** JWT 는 서버에 저장하지 않으므로 로그아웃해도 `exp` 까지 유효하다. 탈취됐을 때 쓸 수 있는 시간이 곧 수명이므로 짧을수록 안전하다.
2. **짧아도 사용자는 불편하지 않다.** access 가 만료되면 프론트 인터셉터가 refresh token 으로 자동 재발급하고 원래 요청을 다시 보낸다 ([05-ui-ux.md 4. API 호출 공통 모듈](05-ui-ux.md#4-api-호출-공통-모듈)). 사용자는 15분마다 로그인하지 않는다.
3. **refresh token 1일 = "하루 안에 다시 쓰면 로그인 유지"**. 회전 방식이라 계속 사용하는 동안에는 만료가 밀려나고, **하루 이상 쓰지 않으면 다시 로그인**한다. 학습용 챗봇의 사용 패턴(하루 단위 학습)에 맞다.
4. **토큰을 브라우저에 저장한다** ([4. 토큰을 프론트에 저장하는 위치 — 위험성과 대안](#4-토큰을-프론트에-저장하는-위치--위험성과-대안)). HttpOnly 쿠키보다 탈취 위험이 있으므로 오래 사는 refresh token 의 수명을 보수적으로 잡았다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| access 60분 / refresh 없음 (이전 초안) | 60분 동안 폐기 불가, 로그아웃이 프론트 토큰 삭제뿐이라 서버가 통제하지 못함 |
| access 60분 / refresh 7일 (중간 초안) | refresh 가 생긴 뒤에는 access 를 길게 둘 이유가 없음. 7일은 브라우저 저장 토큰으로는 길다 |
| refresh 30일 | 로그인 유지 편의는 크지만 탈취 시 피해 기간이 너무 김 |

### 한계와 보완
- 15분 동안은 로그아웃한 access token 도 유효하다 → 수명을 짧게 둔 것 자체가 보완책이다.
- refresh token 탈취 시 공격자가 먼저 재발급하면 원래 사용자의 토큰은 무효가 되어 **다음 요청에서 로그인 화면으로 이동**한다 → 회전 덕분에 탈취가 드러난다.

## 2. AI 컨텍스트 최근 성공 Q/A 5개

### 결정
`AI_CONTEXT_TURNS=5` — 같은 사용자의 최근 **성공** 질문·응답 5쌍을 현재 질문 앞에 붙여 보낸다. 재시도 횟수와는 관계없다.

### 근거
1. **mission 4-3절** 은 "최소한의 컨텍스트 구성 전략" 을 요구하고 예시로 "최근 N개의 대화" 를 든다. mission 7절의 대화 예시("내가 방금 뭘 물어봤지?")는 최소 1개만 있어도 되지만, 실제 학습 대화는 2~4번 이어서 묻는 경우가 많다.
2. **이전 답변 길이에는 상한이 없다.** 질문은 1000자로 막아도 AI 답변은 길 수 있어서, N 이 커지면 프롬프트가 급격히 커진다 → 토큰 비용·응답 지연 증가 → 30초 타임아웃에 걸릴 위험도 커진다.
3. **5 는 "직전 흐름을 기억" 과 "프롬프트 크기 통제" 의 절충**이다. 개수로 자르므로 구현이 단순하고 설명하기 쉽다.
4. 값은 환경변수라 **운영 중 조정 가능**하다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 1개 (직전 Q/A 만) | "아까 두 번째로 물어본 것" 같은 연속 질문을 처리하지 못함 |
| 전체 대화 | 대화가 쌓일수록 비용·지연이 무한히 증가 |
| 요약 기반 컨텍스트 | 요약용 AI 호출이 추가로 필요해 실패 지점·비용 증가, 필수 범위 초과 |
| 글자 수 기준 자르기 | 더 정밀하지만 구현·검증이 복잡. 필요하면 추후 상한 추가 |

## 3. AI 응답 대기 30초

### 결정
`AI_TIMEOUT_SECONDS=30` — Codyssey AI API 호출 **전체**를 30초로 제한한다. 초과하면 `code: 504`. httpx 타임아웃은 연결·읽기 단계별로 적용되므로 호출 전체를 `asyncio.timeout(30)` 으로 감싼다 ([02-architecture.md 5-4. 챗 파이프라인 `POST /api/chat` (핵심)](02-architecture.md#5-4-챗-파이프라인-post-apichat-핵심)).

### 근거
1. **mission 6절** 은 "AI API 호출은 타임아웃을 설정해야 하며(값은 팀이 선택)" 이라고 요구한다.
2. **너무 짧으면 정상 응답을 끊는다.** 생성형 AI 는 답변 길이·컨텍스트 크기에 따라 수 초~십수 초가 걸린다. 컨텍스트 5쌍이 붙으면 더 길어질 수 있다.
3. **너무 길면 사용자가 떠나고 서버 자원이 묶인다.** 30초가 지나도 응답이 없으면 대부분 장애 상황이므로, 빨리 실패를 알리고 [다시 시도] 를 선택하게 하는 편이 낫다.
4. 대기 중에는 로딩 표시가 있어 30초까지는 "처리 중" 으로 인지된다.
5. 환경변수라 실측 후 조정 가능하다 (실제 응답시간은 관리자 통계 `avg_latency_ms` 로 확인).

### 한계
- Codyssey AI API 의 권장 타임아웃·호출 제한은 아직 확인하지 못했다 ([11-open-issues.md](11-open-issues.md) F1). 실측값에 따라 조정한다.

## 4. 토큰을 프론트에 저장하는 위치 — 위험성과 대안

### 결정
**`localStorage`** (확정 — [11-open-issues.md 0. 확정되어 문서에 반영한 것](11-open-issues.md#0-확정되어-문서에-반영한-것) A15). access·refresh token 을 같은 곳에 두고, refresh token 은 요청 body 로 보낸다.
키 이름: `auth:access_token` · `auth:refresh_token`
접두어는 **관심사**(`auth:`)로 나눈다. `localStorage` 는 이미 도메인 단위로 격리되므로 서비스명을 접두어로 쓰지 않는다.
읽기·쓰기·삭제는 `src/utils/tokenStorage.ts` 한 곳에서만 하고, 변경은 구독으로 알린다 ([17. 토큰 변경을 useSyncExternalStore 로 구독](#17-토큰-변경을-usesyncexternalstore-로-구독)).

### 왜 브라우저에 저장해야 하나
JWT 는 서버가 세션을 보관하지 않으므로, 클라이언트가 토큰을 들고 있다가 요청마다 보내야 한다. 저장 위치의 선택지는 아래 세 가지다.

| 위치 | 새로고침 후 유지 | XSS 로 탈취 | CSRF | 크로스 도메인(Railway 2개 도메인) |
|------|:----------------:|:-----------:|:----:|------------------------------------|
| **메모리** (React 상태) | ❌ 새로고침하면 사라짐 | 어려움 (실행 중 스크립트는 여전히 요청 가능) | 해당 없음 | 문제없음 |
| **localStorage** | ✅ | **가능** — 악성 스크립트가 `localStorage` 를 읽어 외부로 전송 | 해당 없음 (자동 첨부 안 됨) | 문제없음 |
| **HttpOnly 쿠키** | ✅ | JS 로 읽을 수 없음 | **대응 필요** (자동 첨부) | `SameSite=None; Secure` + CORS `allow_credentials` 필요, 서드파티 쿠키 차단 정책 영향 |

### localStorage 를 택한 이유
1. **요구사항**: 새로고침해도 로그인 상태가 유지되어야 한다 (`GET /api/auth/me` 로 복원). 메모리만으로는 불가능하다.
2. **배포 구조**: 프론트와 백엔드가 다른 도메인이라 쿠키 방식은 크로스 사이트 쿠키가 되어 설정이 복잡하고 브라우저 정책에 막힐 수 있다 ([02-architecture.md 4. 인증 방식 결정: JWT vs 서버 측 세션](02-architecture.md#4-인증-방식-결정-jwt-vs-서버-측-세션)).
3. **CSRF 가 성립하지 않는다**: 토큰을 헤더에 직접 넣으므로 다른 사이트가 사용자 몰래 인증 요청을 보낼 수 없다.

### 위험성
- **XSS(악성 스크립트 실행)가 발생하면 토큰이 탈취된다.** 이것이 localStorage 의 가장 큰 약점이다.

### 해시·암호화해서 저장하면 안전한가 — 아니다

| 방식 | 왜 안 되는가 |
|------|--------------|
| 해시로 저장 | 해시는 단방향이라 원래 토큰을 복원할 수 없다 → 서버에 보낼 값을 만들지 못해 로그인 자체가 불가능 |
| 암호화해서 저장 | 복호화 키도 브라우저(JS 번들·스토리지)에 있어야 한다 → 스크립트를 실행할 수 있는 공격자는 키까지 가져간다 |
| 공통 한계 | XSS 공격자는 토큰을 읽지 않고도 **이미 로그인된 상태로 API 를 직접 호출**할 수 있다 |

→ 저장 방식은 방어선이 되지 못하므로, **XSS 를 발생시키지 않는 것**과 **발생 시 피해 시간을 줄이는 것** 두 축으로 대응한다.

### 보완
| 보완책 | 효과 |
|--------|------|
| access token 15분 | 탈취돼도 짧은 시간만 사용 가능 |
| refresh token 1일 + 회전 | 탈취 후 공격자·사용자 중 한쪽이 재발급하면 다른 쪽 토큰이 무효 → 탈취가 드러남 |
| 로그아웃 시 서버에서 refresh 폐기 | 로그아웃 후 재발급 차단 |
| React 기본 이스케이프 유지, `dangerouslySetInnerHTML` 금지 | XSS 발생 가능성 자체를 낮춤 (AI 답변도 텍스트로만 렌더링) |
| 외부 스크립트 미삽입 | 공급망 스크립트를 통한 탈취 경로 차단 |
| 의존성 최소화 · 사용자 입력을 `href`/`src` 에 직접 넣지 않음 | XSS 유입 경로 축소 |

### 대안 (나중에 강화한다면)
| 대안 | 방법 | 비용 |
|------|------|------|
| **access 는 메모리, refresh 는 HttpOnly 쿠키** | 새로고침 시 쿠키의 refresh 로 access 재발급 | 쿠키·CORS `credentials`·`SameSite=None`·CSRF 대응 추가 — 보안 표준에 가장 가깝지만 크로스 도메인이라 복잡 |
| 프론트가 `/api` 를 같은 도메인으로 프록시 | Railway 프론트 서버가 백엔드로 전달 → 쿠키가 같은 사이트 쿠키가 됨 | 프록시 설정 파일 추가, 배포 구조 변경 |
| sessionStorage | 탭을 닫으면 삭제 | 탭 간 로그인 공유 안 됨, XSS 위험은 localStorage 와 같음 |

## 5. 질문 최대 1000자

### 결정
`MAX_MESSAGE_LENGTH=1000` — 앞뒤 공백을 뺀 질문이 1~1000자가 아니면 `code: 422`. 프론트 입력창도 1000자에서 막고 카운터를 보여준다. **사용자가 한 번에 보내는 질문 길이** 제한이며, AI 에 보내는 전체 프롬프트 제한은 아니다.

### 근거
1. **mission 4-5절** 는 "사용자 입력 검증 로직이 최소 1개 이상" 을 요구하고 예로 "빈 입력 차단, 길이 제한" 을 든다. 둘 다 적용했다.
2. **프롬프트 크기 통제**: 전체 프롬프트 = 컨텍스트 5쌍 + 현재 질문. 질문에 상한이 없으면 한 요청이 매우 커져 비용·지연·타임아웃 위험이 커진다.
3. **학습 질문에 충분한 길이**: 한글 1000자는 에러 메시지나 짧은 코드 조각을 붙여 질문하기에 충분하다.
4. **남용 방지**: 긴 문서를 붙여넣어 쿼터를 소모하는 사용을 막는다.
5. **서버 검증이 기준**: 프론트 제한은 편의일 뿐, API 를 직접 호출하면 우회되므로 서버에서 반드시 검사한다.

### 한계
- 긴 코드 전체를 붙여넣는 질문은 불가능하다. 필요하면 값만 늘리면 된다(환경변수).

## 6. 응답 형식 `{code, data}` · HTTP 200 고정

### 결정
- 모든 응답: `{ "code": number, "data": object }`. 실패 시 `data = { "message": "..." }`
- 서버가 처리한 응답은 성공·실패 모두 **HTTP 200**, 결과는 body `code` 로 판단
- FastAPI 기본 에러(입력 검증 422, 404, 405, 500)도 예외 핸들러로 같은 형태로 변환
- body 에 `code` 가 없는 응답(네트워크 끊김, Railway 앞단 502/503) = **서버 연결 실패**

### 근거
1. **프론트 처리 단일화**: 모든 응답이 같은 모양이라 인터셉터 하나에서 `code` 만 보고 성공·실패를 판단한다. axios 가 4xx/5xx 에서 예외를 던지는 흐름과 정상 흐름을 나눠 처리할 필요가 없다.
2. **"서버가 처리한 실패" 와 "서버에 닿지 못한 실패" 가 명확히 구분된다.** 봉투가 있으면 우리 서버가 판단한 결과이고, 봉투가 없으면 인프라 문제다. 사용자 안내 문구를 정확히 고를 수 있다.
3. **mission 4-5절 "오류 응답(메시지/상태코드/안내)"** 을 충족한다 — `code`(상태코드 체계의 숫자) + `data.message`(안내 문구).
4. **FastAPI 기본 형식(`{"detail": ...}`)을 그대로 두지 않는다**: 검증 에러만 다른 모양이면 프론트 분기가 늘어나고 사용자에게 영어 기술 메시지가 노출된다.

### 버린 대안과 트레이드오프
| 대안 | 장점 | 버린 이유 |
|------|------|-----------|
| HTTP 상태코드 = body code | 브라우저 개발자도구·로그에서 실패가 바로 보임 | 팀이 결과 판단을 body 한 곳으로 통일하는 쪽을 선택 |
| 문자열 에러 코드 포함 (`error: "AI_TIMEOUT"`) | 같은 401 의 원인 구분이 쉬움 | 응답 형식을 최소화. 원인은 요청 API 로 구분(로그인 API 401 = 로그인 실패) |

### 한계와 보완
- Railway·브라우저 Network 탭에서 실패도 200 으로 보인다 → 서버 로그와 `server_logs` 에 `code` 를 기록해 추적하고, 관리자 화면에서 실패 기록을 본다.

| 결정 | 근거 |
|------|------|

| 로그인 실패 메시지 통일 | 이메일/비밀번호 중 무엇이 틀렸는지 알리면 가입된 이메일을 알아낼 수 있다 |

## 9. access + refresh token · 로그아웃 API

### 결정
- access token = JWT(서버 미저장, 15분)
- refresh token = 무작위 문자열, **SHA-256 해시로 `refresh_tokens` 에 저장**(1일), 재발급 시 회전
- `POST /api/auth/refresh` 재발급, `POST /api/auth/logout` 은 refresh 행 삭제
- 만료 행은 하루 1회 스케줄러가 삭제, 여러 기기 로그인 허용(기기별 로그아웃)

### 근거
1. **mission 4-2절** 회원가입·로그인·인증 상태별 접근 제어를 충족하면서, "왜 이 방식인가" 를 설명할 수 있어야 한다.
2. **JWT 를 쓰는 이유**: 프론트·백엔드가 다른 도메인이라 쿠키 세션은 크로스 사이트 쿠키 설정이 필요하다. Authorization 헤더 방식은 도메인과 무관하고 CSRF 대응이 필요 없다.
3. **refresh token 을 더한 이유**: JWT 만 쓰면 "짧은 수명(안전)" 과 "로그인 유지(편의)" 가 충돌하고, 로그아웃해도 서버가 막을 수 없다. refresh token 을 DB 에 두면 둘 다 해결된다.
4. **무작위 문자열 + 해시 저장**: refresh token 은 어차피 DB 에서 확인·폐기해야 하므로 JWT 형식의 장점(DB 조회 없는 검증)이 없다. 무작위 값은 정보가 들어 있지 않고, 서명 키가 유출돼도 위조되지 않으며, DB 가 유출돼도 해시만 있어 쓸 수 없다. 384비트 무작위 값이라 bcrypt 같은 느린 해시 없이 SHA-256 으로 충분하고 인덱스 조회가 가능하다.
5. **회전**: 한 번 쓴 refresh token 은 즉시 무효가 되어 탈취된 토큰의 재사용 기간이 줄고, 공격자·사용자가 동시에 쓰면 한쪽이 실패해 탈취가 드러난다.
6. **만료 행 스케줄러**: 만료 판단은 평문 `expires_at` 컬럼으로 하므로 토큰을 해독할 필요가 없다. 보안에는 영향이 없지만(조회 시 만료 제외) 테이블이 계속 커지는 것을 막는다.

### refresh token 을 왜 회전하는가 — XSS 와 묶어서 보기

**전제**: 토큰을 `localStorage` 에 저장한다([4. 토큰을 프론트에 저장하는 위치 — 위험성과 대안](#4-토큰을-프론트에-저장하는-위치--위험성과-대안)). XSS 가 발생하면 토큰은 읽힌다고 가정해야 하며, 저장 방식을 바꿔도(해시·암호화) 막을 수 없다.
그래서 방어를 **"탈취를 못 하게"** 가 아니라 **"탈취해도 오래 못 쓰게 + 탈취를 알아채게"** 로 설계했다.

**회전 없이 1일짜리 refresh token 을 그대로 두면**
```
공격자가 refresh token 탈취 → 24시간 동안 access token 을 계속 재발급 → 사용자·서버 모두 모름
```

**회전하면 (재발급마다 이전 토큰 폐기)**
```
공격자가 R1 탈취
 ├ 사용자가 먼저 재발급 → R1 폐기, 사용자 R2 → 공격자의 R1 은 그 순간 무력화 ✅
 └ 공격자가 먼저 재발급 → R1 폐기, 공격자 R2 → 사용자의 다음 재발급이 401
                                          → 사용자가 갑자기 로그인 화면으로 이동 → 이상 징후로 드러남 ✅
```

| 회전이 주는 것 | 설명 |
|----------------|------|
| 탈취 토큰의 유효 시간 단축 | 최대 1일 → **다음 재발급 시점까지**(활성 사용자는 보통 15분 내외) |
| 탈취 감지 가능성 | 정상 사용자와 공격자가 같은 토큰을 쓰면 **한쪽이 반드시 실패**한다. 서버 로그에서 무효 refresh 사용을 관찰할 수 있다 |
| 로그아웃과의 결합 | 로그아웃 시 서버가 refresh 행을 삭제 → 그 이후 재발급 경로가 완전히 닫힌다 |

| 회전이 주지 못하는 것 | 보완 |
|----------------------|------|
| 탈취 자체를 막지는 못함 | XSS 예방([4. 토큰을 프론트에 저장하는 위치 — 위험성과 대안](#4-토큰을-프론트에-저장하는-위치--위험성과-대안): `dangerouslySetInnerHTML` 금지·외부 스크립트 미삽입·의존성 최소화) |
| 이미 탈취된 access token(최대 15분) | access 수명을 15분으로 짧게 유지 |
| 동시 재발급으로 인한 오탈락 | 프론트 single-flight 처리([15. 토큰 재발급 동시성 — single-flight](#15-토큰-재발급-동시성--single-flight)) — 정상 사용자가 회전 때문에 튕기지 않도록 |

> 정리: **localStorage 저장(편의·요구사항) → XSS 탈취 가능성 인정 → 회전 + 짧은 수명 + 서버 폐기로 피해 시간과 발각 가능성을 관리**하는 구조다.

### 한계
- 로그아웃해도 access token 은 최대 15분 유효하다 → 수명을 짧게 둔 이유다.

## 10. 관리자 기능 5종 필수

### 결정
사용자 목록·검색 / 사용자별 대화 / AI 실패 기록 / 요약 통계 / request_id 요청 흐름 로그. 조회 전용, 관리자는 `.env` 시드로만 생성, 권한은 매 요청 DB 의 `role` 로 확인.

| 4-4절 "사용자 기준 로그 조회/추적" — 예: 관리자 조회 API/화면 | 사용자 목록 → 사용자별 대화 |
| 4-5절 "AI 실패/타임아웃 … 로그로 원인을 추적" (3절 과제 목표) | AI 실패 기록 → request_id → 요청 흐름(`request_received → ai_call_failed → db_save_*`) |
| 4-5절 서버 로그 4종 | 로그가 실제로 남는다는 것을 화면으로 시연 |

- **조회 전용**: 필요한 권한만 부여(최소 권한). 수정·삭제 기능이 없으면 오조작·권한 남용 위험이 없다.

- **토큰에 role 미포함, DB 확인**: 권한을 회수하면 즉시 반영된다.
- **기간·상태 필터 제외**: 추적 요구를 충족하는 데 필수는 아니어서 범위에서 뺐다.

## 11. Railway 서비스 2개 배포

## 13. AI 실패 시 자동 재시도 없음 · [다시 시도] 버튼

### 결정
서버는 AI 호출 실패 시 즉시 504/502 로 안내한다. 사용자가 오류 말풍선의 [다시 시도] 버튼을 누르면 같은 질문으로 새 요청을 보낸다.

### 근거
1. **mission 4-5절**: 실패 시 서비스가 멈추지 않고 "오류가 발생했음을 알리는 응답" 을 줘야 한다. 즉시 안내가 요구에 가장 직접적으로 맞다.
2. **대기시간 누적 방지**: 타임아웃 30초에서 서버가 자동으로 2번 더 시도하면 사용자는 최대 90초를 기다린다.

4. **사용자 통제**: 질문을 고칠지, 잠시 뒤 다시 할지 사용자가 선택한다.
5. **추적이 단순**: 요청 1번 = `request_id` 1개 = `chat_logs` 1행. 재시도는 새 요청으로 기록되어 관리자 화면에서 실패와 재시도가 구분된다.

## 14. 프론트엔드 TypeScript (strict)

### 결정
프론트를 **TypeScript 로 작성**한다 (`strict: true`). 기존 JavaScript(JSX) 골격은 화면 구현 전에 전환했다(완료).
`npm run typecheck`(`tsc --noEmit`)를 두고, `npm run build` 는 타입 검사를 먼저 수행한다.

### 근거
1. **API 계약을 타입으로 고정한다.** 우리 응답은 `{code, data}` 봉투이고 `data` 모양이 API 마다 다르다. 백엔드·프론트가 병렬로 구현하므로, 필드명이 다르거나(`chat_id` vs `id`) 응답 형태가 바뀌면 **빌드 단계에서 드러나야** 한다.
   ```ts
   type ApiResponse<T> = { code: number; data: T }
   type User = { id: number; email: string; nickname: string; role: 'user' | 'admin' }
   type AdminChatItem = { chat_id: number; question: string; answer: string | null
                          status: 'success' | 'error'
                          error_code: 'AI_TIMEOUT' | 'AI_CALL_FAILED' | null
                          latency_ms: number | null; request_id: string; created_at: string }
   ```
2. **결과 코드 분기 누락을 막는다.** 401·403·404·409·422·500·502·504 + 봉투 없음까지 처리 분기가 많다. 유니온 타입으로 두면 빠진 분기를 컴파일러가 알려준다.
3. **`answer: string | null`(실패 기록) 처럼 null 이 오는 필드**를 strict 모드가 강제로 처리하게 한다 — 관리자 화면에서 실패 대화를 렌더링할 때 흔한 런타임 오류를 예방한다.
4. **지금이 가장 싸다.** 현재 소스는 `main.jsx`·`App.jsx` 두 개뿐이다. 화면 10여 개를 만든 뒤 전환하면 대형 PR 이 되어 리뷰가 어렵다.
5. 팀 문서에 프론트 언어 규정이 없었고(프론트 담당 결정 사항), **백엔드·API 계약에는 영향이 없다.**

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| JavaScript 유지 + JSDoc 타입 | 에디터 힌트는 얻지만 빌드 차원의 강제력이 약하고, 표기가 장황하다 |
| TypeScript 를 나중에 도입 | 파일이 늘수록 전환 비용·PR 크기가 커진다 |
| `strict: false` 로 시작 | `null` 처리 강제가 빠져 위 3번 이점을 잃는다. 나중에 켜면 오류가 한꺼번에 쏟아진다 |

### 한계와 보완
- 타입 작성에 시간이 조금 더 든다 → API 응답 타입은 [03-api.md](03-api.md) 예시를 그대로 옮기면 되므로 부담이 작다.
- 타입은 **런타임 검증이 아니다.** 서버가 다른 모양을 보내도 타입이 막아주지 않으므로, 인터셉터에서 봉투 형태(`typeof code === 'number'`)를 실제로 확인한다 ([05-ui-ux.md 4. API 호출 공통 모듈](05-ui-ux.md#4-api-호출-공통-모듈)).

## 15. 토큰 재발급 동시성 — single-flight

### 결정
프론트 axios 인터셉터에서 **재발급 요청을 동시에 1건만** 보낸다. 여러 요청이 같은 시점에 `code: 401` 을 받아도 `POST /api/auth/refresh` 는 한 번만 호출하고, 나머지는 그 결과를 **함께 기다렸다가** 새 access token 으로 재시도한다 ([05-ui-ux.md 4. API 호출 공통 모듈](05-ui-ux.md#4-api-호출-공통-모듈)의 `refreshing` 공유 Promise).

### 왜 필요한가 — 회전(rotation)과의 관계
refresh token 은 **재발급할 때마다 회전**한다(이전 토큰 즉시 폐기, [9. access + refresh token · 로그아웃 API](#9-access--refresh-token--로그아웃-api)·[1. access token 15분 · refresh token 1일](#1-access-token-15분--refresh-token-1일)). 그래서 동시 재발급이 일어나면 이렇게 깨진다.

```
(access 만료 직후 화면 진입 — /auth/me · /me/chats 두 요청이 동시에 401)

single-flight 없음                         single-flight 적용
 요청A → refresh(R1) → R2 발급, R1 폐기      요청A → refresh(R1) 시작 ─┐
 요청B → refresh(R1) → R1 은 이미 폐기 → 401  요청B → 진행 중인 요청에 합류 ┘
        → 사용자 강제 로그아웃 ❌                    → R2 저장 → A·B 모두 재시도 성공 ✅
```

챗 화면 진입처럼 **한 화면에서 API 를 2개 이상 호출하는 곳**(`/auth/me` + `/me/chats`, 관리자 화면의 stats + users)에서 실제로 발생한다. 탭을 여러 개 열어도 같은 문제가 생긴다.

### 구현 규칙
| 항목 | 규칙 |
|------|------|
| 공유 | 모듈 스코프에 `refreshing: Promise \| null` 하나를 두고, 없을 때만 재발급 요청 생성 |
| 합류 | 이미 있으면 그 Promise 를 `await` 해서 결과를 공유 |
| 정리 | 성공·실패와 무관하게 `finally` 에서 `refreshing = null` |
| 재시도 | 재발급 성공 시 원래 요청을 **1회만** 재시도 (`_retried` 플래그로 무한 루프 방지) |
| 실패 | 재발급이 실패하면 `clearTokens()` 호출 → 저장소 구독자에게 전파 → `AuthStatus` 가 `anonymous` → 가드가 로그인 화면으로 ([17. 토큰 변경을 useSyncExternalStore 로 구독](#17-토큰-변경을-usesyncexternalstore-로-구독)) |
| 제외 | 로그인·재발급·로그아웃 API 의 401 은 이 흐름을 타지 않는다 (로그인 실패는 폼에서 처리) |

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 각 요청이 알아서 재발급 | 위 시나리오대로 회전 때문에 로그아웃이 발생 |
| 회전을 없애 동시성 문제 제거 | 탈취 감지·무효화 수단을 잃는다 ([9. access + refresh token · 로그아웃 API](#9-access--refresh-token--로그아웃-api)) |
| 서버가 폐기 직후 이전 토큰을 몇 초간 허용(유예) | 서버 구현이 늘고 탈취 토큰의 유효 시간이 생긴다. 프론트에서 해결되는 문제라 범위 밖 — 필요해지면 팀 논의 |

### 한계
- **재발급 자체는 탭 간에 공유되지 않는다.** `refreshing` 은 모듈 스코프 변수라 탭마다 따로 존재한다. 서로 다른 탭이 동시에 재발급하면 한쪽은 로그인 화면으로 갈 수 있다. 빈도가 낮고 다시 로그인하면 복구되므로 현재 범위에서는 감수한다 (필요 시 `BroadcastChannel` 로 확장).
- 다만 **결과 반영은 탭 간에 동기화된다.** `tokenStorage.subscribe` 가 `storage` 이벤트를 함께 구독하므로, 한 탭에서 로그아웃하면 다른 탭도 즉시 로그인 화면으로 이동한다 ([17. 토큰 변경을 useSyncExternalStore 로 구독](#17-토큰-변경을-usesyncexternalstore-로-구독)).

## 17. 토큰 변경을 useSyncExternalStore 로 구독

### 결정
`utils/tokenStorage.ts` 가 토큰을 저장·삭제할 때 **구독자에게 알리고**, React 쪽은 `hooks/useAccessToken.ts`(`useSyncExternalStore`)로 그 변화를 받는다.

### 문제
인터셉터는 재발급이 최종 실패하면 토큰을 지워야 한다. 그런데 **토큰만 지우면 화면은 그대로다.** 헤더에 닉네임이 남고 가드는 여전히 통과시킨다. React 는 상태가 바뀌어야 다시 그리는데, `localStorage` 조작은 React 입장에서 아무 일도 아니기 때문이다.
`storage` 이벤트도 답이 되지 못한다. **같은 탭에서 바꾼 경우에는 발생하지 않는다.**

### 왜 인터셉터가 AuthContext 를 직접 부르면 안 되는가
`setUser` 는 `AuthContext` 안에만 있다. 이를 쓰려고 `api/interceptors/refresh.ts` 에서 `store/AuthContext` 를 import 하면 순환 참조가 된다.

```
AuthContext → api/auth → api/instance → interceptors → AuthContext
```

모듈이 서로를 기다리다 한쪽이 **미완성 상태(`undefined`)로 평가**된다. 타입 검사와 빌드는 통과하고 실행 시점에만 깨지며, 에러 메시지가 원인을 가리키지 않아 추적이 어렵다. `useAuth` 는 훅이라 컴포넌트 밖인 인터셉터에서 호출할 수도 없다.

### 채택한 구조
`tokenStorage` 를 **아무것도 import 하지 않는 끝점**으로 두고 양쪽이 이것만 참조한다.

```
interceptors ──→ tokenStorage ←── AuthContext
```

인터셉터는 `clearTokens()` 만 호출하고 `AuthContext` 의 존재를 모른다.

### 주의
`getSnapshot` 은 **원시값**(문자열·`null`)을 반환해야 한다. 매번 새 객체를 반환하면 `Object.is` 비교가 항상 거짓이라 무한 리렌더에 빠진다. 토큰 두 개를 함께 봐야 하면 훅을 나눈다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| `window.dispatchEvent(new CustomEvent(...))` | 동작하지만 이벤트 이름이 문자열이라 오타가 조용히 실패하고, 테스트에 DOM 환경이 필요하며, 누가 구독하는지 코드로 추적되지 않는다 |
| 콜백 등록 모듈(`setUnauthorizedHandler`) 분리 | 순환은 피하지만 파일이 하나 더 생긴다. 상태의 근원이 토큰 하나라 저장소가 직접 알리는 편이 단순하다 |
| `useState` + `useEffect` 로 구독 | 첫 렌더와 `useEffect` 실행 사이의 변경을 놓친다 |

## 18. 상태 관리는 Context API — Zustand 미도입

### 결정
전역 상태는 **Context API** 로 관리한다 ([02-architecture.md 1. 기술 스택](02-architecture.md#1-기술-스택)).

### 근거
Context 가 들고 있는 것은 `user`(id·email·nickname·role)와 `AuthStatus` 뿐이고, **로그인·로그아웃·재발급 최종 실패 시점에만** 바뀐다. 세션당 2~3회다.
**access token 은 Context 에 넣지 않는다.** `localStorage` 에 두고 인터셉터가 직접 읽고 쓰므로, 15분 주기 교체가 Context 를 건드리지 않는다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| Zustand 등 전역 상태 라이브러리 | 스토어가 하나뿐이고 갱신 빈도가 낮다. 컴포넌트 밖에서 값을 읽어야 하는 요구도 `tokenStorage` 로 해결된다 |

### 한계와 보완
Context 는 **값의 참조가 바뀌면 구독 컴포넌트를 모두 리렌더**한다(`Object.is` 비교). selector 가 없어 일부 값만 골라 구독할 수 없고 `React.memo` 로도 막히지 않는다.
→ Provider 의 `value` 를 `useMemo` 로, 액션 함수를 `useCallback` 으로 고정한다. 구독 컴포넌트가 적고 갱신이 드물어 현재 범위에서는 이것으로 충분하다.

## 19. TanStack Query 미도입

### 결정
서버 데이터 캐싱 라이브러리를 쓰지 않고, 조회는 `useAbortableRequest` 훅으로 직접 다룬다.

### 근거
1. **통신 계층 작업량이 줄지 않는다.** TanStack Query 는 캐시 층이고 실제 요청은 우리 함수(axios)가 보낸다. 응답 형식 정규화·토큰 첨부·재발급 single-flight 는 그대로 만들어야 한다.
2. **요청 취소도 이점이 아니다.** 엔드포인트가 `signal` 을 받는 것과 인터셉터가 취소를 통과시키는 것은 어느 쪽이든 필요하다. 컴포넌트의 반복 코드는 `useAbortableRequest` 훅 하나로 제거된다.
3. **캐시가 필요할 만큼 복잡하지 않다.** 대화 로그는 무한 스크롤이 아니라 **[더 보기] 버튼**이라 `offset` 누적으로 충분하다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| TanStack Query 도입 | 위 근거 외에, 로그아웃 시 `queryClient.clear()` 를 빠뜨리면 **다른 계정으로 로그인했을 때 이전 사용자 데이터가 보이는** 사고가 생긴다. 얻는 것에 비해 위험이 크다 |

### 한계
관리자 화면처럼 조회 지점이 늘면 컴포넌트마다 로딩·에러 상태를 다루게 된다. 화면 구현 중 반복이 과해지면 그 시점에 다시 판단한다.

## 20. React Compiler 미도입

### 결정
React Compiler 를 빌드에 넣지 않고, 필요한 곳에만 `useMemo`·`useCallback` 을 쓴다.

### 근거
컴파일러는 자동 메모이제이션을 넣어 주지만 **자동으로 켜지지 않고** 별도 설정이 필요하다. 그런데 이 앱에서 메모이제이션이 필요한 지점은 **Context value 한 곳뿐**이라 `useMemo` 한 줄로 끝난다. 화면 5개에 상태 변화도 적어 성능 차이가 체감되지 않는다.

### 한계
챗 화면에서 메시지 목록이 길어져 리렌더가 실제로 문제가 되면 그때 도입을 재검토한다. 도입하면 손으로 넣은 `useMemo`·`useCallback` 은 제거할 수 있다.

## 21. 동시 요청 — 연결 풀 없이(NullPool), 챗 DB 작업은 별도 스레드

### 결정
SQLite 파일 DB 는 연결 풀(미리 열어 둔 연결을 돌려 쓰는 장치) 없이 요청마다 연결을 열고 닫는다(`NullPool`, #72·PR #74). 챗 API 안의 DB 작업(대화 기록 조회·대화 저장·서버 로그 저장)은 `asyncio.to_thread` 로 별도 스레드에서 실행한다(#97·PR #98).

### 근거
1. **풀 고갈**: SQLAlchemy 기본 풀은 연결을 최대 15개까지만 만든다. 챗 요청은 AI 응답을 기다리는 최대 30초 동안 연결을 잡고 있어, 동시 요청 15건이면 풀이 바닥나고 다음 요청은 연결을 기다리며 멈췄다. SQLite 는 연결이 곧 파일 열기라 비용이 작아 풀 없이도 충분하다.
2. **이벤트 루프 멈춤**: FastAPI 의 `async def` 함수는 하나의 이벤트 루프(요청들을 번갈아 처리하는 실행 흐름) 위에서 돈다. 그 안에서 동기 DB 코드를 그대로 부르면, SQLite 쓰기 잠금을 기다리는 동안(최대 5초) 루프 전체가 멈춰 **다른 사용자의 로그인·조회까지 함께 멈춘다.** 별도 스레드로 보내면 기다리는 동안에도 루프는 다른 요청을 처리한다.
3. **측정**: 로컬에서 가장 오래 멈춘 시간이 동시 챗 200건 0.65초 → 0.03초, 쓰기 잠금 3초 중 챗 50건 2.6초 → 0.02초로 줄었다. 회귀 테스트는 DB 쓰기 잠금을 2초 잡은 동안 루프가 0.5초 넘게 멈추지 않는지 확인한다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 풀 크기만 늘리기 | 숫자만 미룰 뿐 동시 요청이 그 수를 넘으면 같은 문제가 난다 |
| 비동기 DB 드라이버(aiosqlite + SQLAlchemy async) | 모든 CRUD·테스트를 async 로 다시 써야 한다. 막히는 지점은 챗 API 한 곳이라 그곳만 스레드로 보내는 것이 변경이 가장 작다 |
| 라우터를 `def`(동기)로 바꾸기 | FastAPI 가 스레드에서 실행해 주지만, AI 호출(`httpx.AsyncClient`)의 `await` 를 쓸 수 없게 된다 |

### 한계와 보완
SQLite 는 쓰기를 한 번에 하나만 한다. 쓰기가 아주 많아지면 PostgreSQL 같은 서버형 DB 로 옮기고 그때는 연결 풀을 다시 쓴다(`database.py` 주석에 기록).

## 22. 요청 횟수 제한 — 메모리 카운터, 실제 IP 는 X-Forwarded-For 마지막 값

### 결정
챗은 사용자별 1분 10회, 로그인 실패는 이메일별 10분 5회·IP 별 10분 20회, 가입은 IP 별 10분 20회까지 받고 넘으면 `code: 429`(#86·PR #87). 횟수는 서버 메모리에서 최근 기간 안의 시각만 남겨 센다(슬라이딩 윈도우).

### 근거
1. **비용·무차별 대입 방어**: 챗을 계속 보내면 AI 비용이 들고 서버가 느려진다. 로그인 실패를 무제한 허용하면 비밀번호를 바꿔 가며 계속 시도할 수 있다.
2. **메모리 카운터**: 서버가 Railway 1개 인스턴스라 Redis 같은 외부 저장소 없이 충분하다. 슬라이딩 윈도우는 분이 바뀌는 순간에 몰아 보내는 우회가 통하지 않는다.
3. **IP 별 한도를 넉넉하게(20회)**: 교육장처럼 여러 사람이 같은 공인 IP 를 쓰면 실패가 합쳐서 세어진다. 이메일별(5회)로 계정을 지키고, IP 별은 한 곳에서 여러 계정을 노리는 경우만 막는다.
4. **X-Forwarded-For(프록시가 원래 접속 IP 를 적어 보내는 헤더)의 마지막 값**: Railway 프록시 뒤에서는 서버가 보는 접속 주소가 모두 프록시다. Railway 는 실제 접속 IP 를 헤더 **끝에** 덧붙이고 앞쪽 값은 사용자가 마음대로 넣을 수 있으므로 마지막 값을 쓴다. 로컬처럼 프록시가 없으면 헤더를 믿지 않는다(`TRUST_FORWARDED_FOR=false`).

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| uvicorn `--forwarded-allow-ips="*"` | 헤더의 **맨 앞** 값을 써서, 헤더를 꾸며 보내면 IP 제한을 피할 수 있다 |
| Redis 같은 외부 저장소 | 서버가 하나라 얻는 것이 없고 관리할 서비스만 늘어난다 |

### 한계와 보완
재배포·재시작하면 횟수가 초기화된다. 서버를 여러 개로 늘리면 저장소를 Redis 등으로 옮겨야 한다. 키가 1만 개를 넘으면 지난 기록을 한 번에 정리해 메모리를 채우는 공격을 막는다.

## 23. 일반 사용자에게 내부 번호를 보이지 않음 — public_id(UUID)

### 결정
`users`·`chat_logs` 에 `public_id`(UUID, 무작위로 만든 128비트 식별자) 컬럼을 두고, 일반 사용자에게 나가는 번호는 이것만 쓴다 — JWT `sub`, 질문 전송·내 대화 로그의 `chat_id`(#99·PR #101, #106·PR #107). 회원가입·내 정보 응답에서는 `id` 를 뺐다. 내부 PK·FK·정렬과 관리자 API 는 정수 id 그대로다.

### 근거
1. **토큰은 누구나 읽을 수 있다**: JWT 는 서명만 할 뿐 암호화하지 않는다. 브라우저에 저장된 토큰을 디코드하면 `sub` 가 그대로 보인다.
2. **순차 번호가 드러내는 것**: 내 사용자 번호로 가입 순서·전체 가입자 수를, 내 최신 대화 번호로 서비스 전체 대화 수·이용량을 알 수 있다.
3. **변경 범위를 작게**: 정수 PK 를 UUID 로 바꾸면 FK·인덱스·관리자 화면까지 모두 바뀐다. 바깥에 보이는 번호만 별도 컬럼으로 두면 DB 구조와 관리자 기능은 그대로다.
4. **관리자 API 는 정수 유지**: 관리자는 이미 모든 사용자를 볼 수 있고 추적이 목적이다. 남의 번호로 바꿔 보는 공격(IDOR)은 `require_admin` 권한 검사로 막는다([13-security-review.md](13-security-review.md) L07).

### 기존 DB 처리
`create_all` 은 이미 있는 테이블에 컬럼을 추가하지 않는다. 서버 시작 때 `add_public_id` 가 ① 컬럼이 없으면 추가 ② 빈 행마다 UUID 채우기 ③ UNIQUE INDEX 생성을 실행한다. 몇 번 실행해도 결과가 같아 Railway 의 기존 `app.db` 를 지우지 않고 맞출 수 있다. 이전 형식(정수 `sub`) access 토큰은 401 이 되지만 refresh 로 새 토큰을 받으므로 다시 로그인할 필요는 없다.

### 한계
SQLite 는 기존 테이블에 기본값 없는 NOT NULL 컬럼을 추가할 수 없어, 기존 DB 의 컬럼은 NULL 허용으로 남는다. 시작할 때 모두 채우고 새 행은 모델 기본값으로 항상 채워진다.

## 24. 운영 방어 기본값 — 본문 64KB · 비밀번호 128자 · API 문서 끄기 · 서명 키 32바이트

| 결정 | 근거 |
|------|------|
| 요청 본문 64KB 넘으면 읽지 않고 `413` (#92·PR #93) | 제한이 없으면 수 MB 요청도 끝까지 메모리에 올린다(2026-10-07 로컬 확인: 5MB 로그인 요청을 그대로 처리). 질문 1000자는 UTF-8 로 약 4KB 라 64KB 면 넉넉하다. `Content-Length` 없이 나눠 보내는(chunked) 요청도 읽은 양으로 끊는다 |
| 비밀번호 최대 128자 (가입·로그인 422) | bcrypt 는 앞 72바이트만 쓰므로 길게 받을 이유가 없다. 로그인의 129자 이상은 비교 자체를 하지 않아 실패 횟수에도 세지 않는다 |
| API 문서 화면(`/docs`·`/redoc`·`/openapi.json`)은 `ENABLE_DOCS=true` 일 때만 (#90·PR #91) | 권한 검사는 되지만, 관리자 API 를 포함한 전체 목록이 공개되면 공격 대상이 한눈에 보인다. 명세는 [03-api.md](03-api.md) 로 제출하고 로컬에서만 켠다 |
| `JWT_SECRET_KEY` 가 비었거나 32바이트 미만이면 서버 시작 거부 (#94·PR #95) | 32바이트(256비트)는 서명 알고리즘 HS256 의 해시 길이와 같아 권장되는 최소 길이다. 키가 짧아 추측되면 아무 사용자의 토큰이나 위조할 수 있다. 잘못된 설정으로 **뜨는 것보다 뜨지 않는 것**이 안전하다 |

## 25. 관리자 계정은 시작할 때마다 환경변수와 맞춤

### 결정
서버가 시작할 때 `ADMIN_EMAIL` 계정을 만들거나 `role=admin` 으로 올리고, 그 밖의 관리자는 `user` 로 내린다(관리자는 항상 1명). 비밀번호는 `ADMIN_PASSWORD` 로 맞추고, 바뀌었으면 그 계정의 refresh 토큰을 모두 폐기한다(#84·PR #85).

### 근거
1. 관리자 이메일을 바꿨을 때 이전 관리자가 권한을 그대로 갖고 있던 문제를 막는다. 권한은 요청마다 DB 의 role 로 확인하므로 내려간 계정의 토큰도 다음 요청부터 403 이다.
2. `ADMIN_EMAIL` 주소로 누군가 먼저 가입해 두면, 그 사람이 정한 비밀번호로 관리자가 되던 문제를 막는다.
3. 비밀번호를 바꾸고 재배포하면 바로 적용되고, 이전 비밀번호로 만든 로그인 세션은 끊긴다.

### 한계
`ADMIN_EMAIL`·`ADMIN_PASSWORD` 가 비었거나 비밀번호가 8~128자를 벗어나면 시드를 건너뛰고 아무도 내리지 않는다 — 설정 실수로 관리자가 0명이 되는 것을 막기 위해서다. 비밀번호를 바꿔도 이미 발급된 access 토큰은 만료(15분)까지 유효하다(토큰을 저장하지 않는 JWT 구조의 한계, [13-security-review.md](13-security-review.md) L03).
